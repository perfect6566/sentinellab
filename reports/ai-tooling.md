# AI tooling and development disclosure

## Runtime Agent versus development assistant

The product Agent is a separate application component. It accepts user requests, calls the configured model provider, validates requested tool names and arguments, executes only the registered malware-analysis tools, and grounds numeric answers in tool results. The classifier and metric calculations remain deterministic Python/model operations.

The deployed service uses the `deepseek` provider (DeepSeek's OpenAI-compatible API at `https://api.deepseek.com/v1`, model `deepseek-chat`) with the server-side key supplied through Render secrets; empty base/model fall back to those defaults, and only `LLM_API_KEY` is required. CI uses a scripted `mock` provider and requires no LLM secret.

## AI-assisted engineering

Codex was used as a coding assistant to inspect requirements, propose and edit application code and tests, explain test failures, and draft technical documentation. All generated changes were reviewed against the project plan, exercised with automated tests or runtime checks appropriate to their scope, and committed by the developer. Reported model scores are taken from saved training/evaluation artifacts rather than generated by the coding assistant.

### What worked well

- **Test-failure triage.** Explaining a failing assertion with the surrounding code in view produced accurate diagnoses faster than reading the trace manually, which was the single largest time saving across the project.
- **Mechanical edits that span many files.** Renaming a schema field or adding a validation rule across the app, tests, and sample data was completed consistently in one pass, which reduced the risk of leaving a stale reference behind.
- **Documentation drafting.** Proposing the structure and wording of the design and evaluation documents gave a usable starting point that was then rewritten against the actual measurements.

### What worked poorly

- **Silent schema drift.** The assistant occasionally produced code that matched a slightly different field name or signature than the one in the project. This only surfaced when the test suite ran, so every suggestion was treated as a draft until a test confirmed it.
- **Over-eager refactoring.** Asked for a fix, the assistant sometimes rewrote surrounding code as well. Those unrelated changes were reverted rather than reviewed line by line, because the diff was larger than the problem.
- **Unverifiable numbers.** Metric values and dataset statistics offered in prose were occasionally wrong or untraceable to a saved artifact. Every figure in the reports was therefore taken from the committed training and evaluation outputs, never from the assistant's recollection.
- **Weak failure-mode awareness.** Suggestions around invalid input, single-class evaluation, and tool timeouts were optimistic about what the code would do. Those paths were re-derived from the specification and covered by explicit tests instead.

## Controls and limits

- Tool dispatch is restricted to `predict_single`, `predict_batch`, and `evaluate_labeled`.
- Server-side validation enforces schemas, session-owned file references, row/size limits, conditional-prediction gates, and per-session result access.
- Numeric answer grounding rejects unsupported values and uncalibrated "confidence" claims.
- Uploaded CSV content is treated as data, not instructions; full CSV contents are not sent as unrestricted model context.
- Deterministic tests use scripted provider responses. Live-provider quality is reported separately with provider/model, scenario records, and failures in `reports/agent-evaluation.md`.

## Reproducibility

The pinned dependencies, test suite, model manifest, training reports, scenario definitions, and public evaluation record are committed. The final explanation and demonstration reflect the developer's own understanding.
